# REPORTING_REQUIREMENTS.md

## Plain-English overview

Reports are how the product proves its value:

- To property owners: "Here's what happened in your apartment this month, with proof."
- To OTAs (Airbnb, Booking): "Here's the evidence for this damage claim."
- To the GM: "Here's how your team is performing."
- To finance: "Here's what's chargeable and what's been recovered."

All reports must come from **structured data**. No report is allowed to depend on AI guesses or free-text scraping.

---

## Required report types

### 1. Inspection report

- One per inspection.
- Includes: property, inspector, template kind, timestamps (started, submitted, reviewed), section-by-section results, all photos with thumbnails.
- Item-level: status (OK / Damaged / Missing / Attention / flagged), notes, photos.
- **"Hide OK items" toggle.** Suppresses any line item with `status = 'ok'` and no flags, so the reader sees only what needs attention. The header still shows the full count ("47 of 50 OK; 3 need attention") so nothing is silently hidden. **On by default for owner-facing output; off by default for internal audit output.** Configurable per export.
- **Flags shown grouped under their parent problem**, not as scattered rows — consistent with `DEDUPLICATION_AND_TASK_GROUPING_RULES.md`. A guest-damage flag that spawned a recovery task + maintenance job appears once, with its child records noted, not three times.
- **Photo rendering rules** (apply to every report that shows photos):
  - Every photo shows its `captured_at` timestamp beneath it ("12 May 2026, 14:23", localised). For dispute/chargeable evidence this is mandatory — the timestamp is the core evidence value.
  - If a photo has a note, the note renders below the timestamp in smaller type.
  - If several consecutive photos share the same note (a **proof-set note** from Evidence Camera Mode), the note renders once above the group with "(applies to next N photos)".
  - Photos are sized for print (no full-resolution overflow); they print acceptably in black-and-white.
- Available as: in-app HTML view (v1.0), native PDF (v1.5).

### 2. Owner monthly report (the headline deliverable)

- One per (company, property, month).
- Built from approved `accountability_records` where `chargeable_party = 'owner'`.
- Includes:
  - Property summary
  - List of chargeable line items with photos, notes, and amounts (estimated or actual)
  - Maintenance work done that month and its cost
  - Inventory movements that fell to the owner
  - Total estimated + total actual
  - A clear "Generated on [date] by [manager]" line
- Status workflow: `draft` (manager edits) → `sent` (visible to Owner Viewer).
- Available as: in-app HTML view (v1.3), native PDF (v1.5), CSV (v1.5).

### 2.5. Owner weekly status update (new in v1.3)

The weekly heartbeat between monthly bills. Keeps owners informed and reduces ad-hoc "what's happening at my property?" messages. Full workflow detail in `OWNER_COMMUNICATION_WORKFLOWS.md`.

- One per (company, property, week).
- Generated by manager from structured data (no hand-curation needed in the happy case).
- Includes:
  - Property status (occupied / between stays / inspection pending / needs attention)
  - Open issues — short list, not full report
  - Resolved issues this week, with cost if any
  - Upcoming maintenance scheduled for next week
  - Pending owner approvals (cross-link to the approval policy flow)
  - Notable inspection findings raised this week (even if not chargeable)
  - Manual occupancy/reservation note (manager free text — PMS integration is v1.5+)
  - Up to 6 evidence-class photo thumbnails
- Deliberately excludes: dollar/rand totals (those belong on the monthly summary), staff names beyond the sending manager, raw audit logs, operational metrics.
- Status workflow: `draft` (manager reviews and edits) → `sent` (visible to Owner Viewer).
- Configurable per property: on/off, day of week (default Sunday evening).
- Auto-skip prompt for weeks with zero activity.
- Available as: in-app HTML view (v1.3), shareable signed link (v1.5).
- Generation cost: ~30 seconds of manager time per property when the system pulls from structured data.

### 3. Maintenance report

- Per company, per period.
- Open issues, in-progress jobs, completed jobs with costs, average time-to-resolution.
- Filterable by property, technician, priority.

### 4. Open issue report

- Lists all `open` and `in_progress` issues across the company (or per property).
- Sorted by priority + age.
- Used by GM and Ops Manager for daily standups.

### 5. Inventory movement report

- All inventory movements per period.
- Filter by movement type, property, chargeable party.
- Trend signals: same item missing repeatedly = process problem.

### 6. Employee performance report (v1.5)

- Per inspector / technician.
- Metrics: inspections completed, average duration, photo counts, items flagged, items overturned by manager.
- Per tech: jobs completed on time, average completion time, repeat-issue rate.

### 7. Audit trail report

- Filtered view of `audit_events` for compliance / dispute use.
- Company Admin and GM only.
- Exportable as CSV.

### 8. OTA evidence pack (v1.5 / v2 — listed here so the data model supports it from day one)

- One per claim.
- Cover sheet + photos with timestamps + inspector and manager signatures (digital) + audit excerpts.
- Exported as a single PDF + a ZIP of original photos.
- **Not built in v1.** The data model captures everything needed; the presentation layer arrives in v1.5/v2.

## Presentation quality requirements (v1 HTML reports) — founder requirement 2026-05-12

HTML reports in v1.0 and v1.3 are not "good enough" placeholders. They are the deliverable that owners and managers actually see. They must be:

### Clean

- No raw IDs, no debug timestamps, no admin-screen leftovers in the rendered output.
- Generous whitespace. Plain typography. Readable on a phone and on a printed A4 page.
- One typeface family. Black-on-white. Subtle dividers, not heavy borders.

### Professional

- Top of the report: company name, property name and address, report type, period covered.
- Bottom of the report: generated-by (manager name), generated-at (date), report status, version note ("Generated from structured data. AI not involved in any numbers.").
- No "powered by [framework]" badges. No watermarks beyond the company name.

### Printable

- The same HTML must print cleanly to A4 via the browser's Print dialog.
- A `@media print` stylesheet hides navigation, sidebars, and any "edit" controls.
- Page breaks fall between sections, never inside a line item with its photo.
- Photos in print are sized so that 2–4 fit on a page without overflow.
- Tables have repeating header rows on each printed page.
- Colours print acceptably in black-and-white (no critical-information-via-colour-only).

### Structured

- Logical section order: header → totals (for owner summary) → per-line items with thumbnails → photo gallery → footer.
- Every number traces back to a row in the database. No "computed in the report" numbers that don't exist in the data.
- Each line item shows: what happened, when, where (room/area), photo thumbnails, who approved (where relevant), amount (where relevant).
- For the owner summary: the **total** is the visual headline at the top, not buried at the bottom.

### Validation checklist (per report type)

A report passes the v1 quality bar when:

- [ ] An owner who is not technical can read the report on their phone without confusion.
- [ ] An owner can print the report on a home printer and the result looks like a finished document.
- [ ] No raw UUIDs, internal status codes, or developer text appear.
- [ ] All photos have appropriate thumbnails (not full-resolution images blowing up the page).
- [ ] Every chargeable amount shows who approved it and when.
- [ ] The footer includes the generation timestamp and the manager who sent it.
- [ ] The "Generated from structured data" line is present.

(These items are also tracked in `TESTING_CHECKLIST.md`.)

## Reporting principles

1. **Structured data only.** Every number in a report is computed from rows, not text.
2. **No AI in the trust path.** AI can *draft* a cover note or *summarise* a comment thread (later), but it never produces the numbers.
3. **Approvals are visible.** Every chargeable amount shows who approved it and when.
4. **Photos are first-class.** Reports show real evidence, not just text.
5. **Owner reports are draftable.** A manager reviews before the owner ever sees it.
6. **Reproducibility.** A report generated today should match a report generated tomorrow if the underlying data hasn't changed.
7. **Audit reports cannot be edited.** Audit reports read directly from `audit_events`.
8. **Print is a first-class output, not an afterthought.** The HTML version must print cleanly. This is what makes the v1.5 native PDF feel like a free upgrade rather than a redesign.

## The owner monthly report — in detail

This is the most important customer-facing report.

### Inputs

- All `accountability_records` for the (company, property, month) where:
  - `chargeable_party = 'owner'`
  - `approved_at IS NOT NULL` (only approved items count)
  - `deleted_at IS NULL`
- All `maintenance_jobs` for that property completed (`status IN ('done', 'verified')`) in the month, where `chargeable_party = 'owner'`.
- All inspection items flagged `owner_chargeable = true` and approved, from inspections submitted in the month.

### Build process

1. Manager opens the **Owner Monthly Summaries** page for a property.
2. Clicks **"Generate / Refresh"** for the target month.
3. The system creates (or updates) an `owner_monthly_summaries` row with `status = 'draft'`.
4. For each input row above, a `owner_monthly_summary_lines` row is created (idempotently — re-generating the same month doesn't duplicate).
5. Totals are computed and stored on the summary row.
6. Manager reviews the summary in the UI, can add notes, can mark individual lines "exclude from summary" with a reason (audited).
7. When ready, manager clicks **"Send"** → `status = 'sent'`, `sent_at = now()`, audit event written.
8. The summary becomes visible to the Owner Viewer for that property.

### What the owner sees

- Property name, month, status (`sent`).
- **Total at the top**, in large type. This is the headline.
- A line per chargeable item: short label, amount (estimated or actual), thumbnail photo (click to enlarge).
- A photo gallery for the month.
- A "Manager notes" block.
- The manager's name and the send timestamp.
- A clean print/save flow via the browser (v1.3) or native PDF (v1.5).

Owner viewers can **not** see:
- Other properties.
- Internal notes flagged as internal-only.
- The audit log.

## Performance considerations

- Reports are read-heavy and computed on demand at MVP scale (hundreds of records per company per month).
- We use plain Postgres **views** (or `WITH` queries) for now, not materialised views.
- If a customer hits real performance issues we add materialised views or a small denormalised reporting table — but that decision waits for evidence.
- PDF generation (v1.5) is async (Edge Function). The UI shows "Generating…" and emails the user when ready, rather than blocking.

## Things we are NOT building in MVP

- A custom report builder (drag-and-drop columns).
- A BI dashboard with pivot tables.
- Scheduled report emails (post-MVP).
- Multi-property roll-ups for owners with multiple apartments (v1.5).
- Tax-aware totals (currency conversions, VAT splits) — v2.
- Auto-translation of reports.
- A separate analytics warehouse (BigQuery, Snowflake, etc.) — v2+ if any customer asks.

## Open questions to revisit

1. Should owners be able to comment on / dispute a line on the summary? — **No in MVP**. They contact the manager outside the app. v1.5 may add a "request review" button.
2. Do we sign PDFs digitally? — Not in MVP. The audit trail is the legal anchor.
3. Do we lock historical reports against edits once sent? — **Yes**. Once `status = 'sent'`, the row and its lines become immutable. A "correction" generates a new summary row and references the old one.
4. Currency? — **ZAR**, single-currency per company in MVP. Multi-currency is post-MVP. (Founder-confirmed 2026-05-12.)
